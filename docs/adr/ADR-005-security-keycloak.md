# ADR-005: Безопасность — Keycloak OAuth2/OIDC + RBAC

## Статус
Принято

## Контекст
API должен аутентифицировать вызывающих, проверять токены (подпись, issuer, audience,
срок действия) и авторизовывать по ролям. Мы не должны строить собственную
аутентификацию, не должны хранить секреты в исходном коде и обязаны следовать
передовым практикам OWASP.

## Решение
Интегрироваться с **Keycloak** как OIDC-провайдером.

- Сервис — это **OAuth2 resource server** (`spring-boot-starter-oauth2-resource-server`).
  Spring Security проверяет подпись JWT по JWK-набору Keycloak и автоматически
  проверяет issuer/audience/срок действия.
- `issuer-uri` настраивается из `KEYCLOAK_ISSUER_URI` (переменная окружения); в
  исходном коде секретов нет.
- Пользовательский `JwtRoleAuthorityExtractor` маппит realm-роли Keycloak
  (`realm_access.roles`) в granted authorities вида `ROLE_*`.
- RBAC-роли:
  - `LOGISTICS_USER` — создание отправлений, отмена своих.
  - `LOGISTICS_OPERATOR` — просмотр отправлений, смена статуса, назначение pickup.
  - `LOGISTICS_ADMIN` — полный доступ.
- Авторизация обеспечивается через `@PreAuthorize("hasAnyRole(...)")` на методах
  контроллеров и глобальную цепочку security-фильтров (все эндпоинты требуют
  действительный токен, кроме Swagger UI и actuator health).
- Сессии stateless (Bearer-токены), CSRF отключён (Bearer-only API), CORS только при
  настройке.
- Локальный realm Keycloak и демо-пользователи предоставляются через
  `docker-compose.yml` и помечены как **только для разработки**.

Меры OWASP: валидация ввода (Bean Validation), отсутствие mass assignment (DTO, а не
сущности), безопасная обработка ошибок (без стектрейсов в ответах), наименьшие
привилегии (по ролям), отсутствие секретов в логах.

## Альтернативы
- **Собственное хранилище JWT/пользователей**: отклонено согласно требованиям.
- **Auth0/Okta**: требуют внешнего SaaS; для self-hosting предпочтителен Keycloak.
- **Stateless opaque-токены**: JWT и так даёт самодостаточные claims; здесь достаточно.

## Последствия
- Централизованное управление идентификацией и ролями в Keycloak.
- Разработчику/оператору необходимо поднять Keycloak (описано в README и compose-файле).
- Для JWT проверка токена локальна (без round-trip интроспекции).
