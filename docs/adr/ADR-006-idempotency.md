# ADR-006: Идемпотентность

## Статус
Принято

## Контекст
Клиенты могут повторять `POST /api/v1/shipments` после сетевого таймаута. Без
дедупликации повторный запрос создаёт лишние отправления. Нужно идемпотентное
создание, возвращающее один и тот же логический ресурс для одного и того же
логического запроса.

## Решение
Поддержать стандартный заголовок `Idempotency-Key` для операций создания.

- Ключ хранится в **PostgreSQL** в таблице `idempotency_keys`, которая несёт
  ограничение `UNIQUE(idempotency_key)`.
- Регистрация использует `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING`, делая
  решение «первый пишущий побеждает» **атомарным** — параллельные запросы с одним
  ключом сходятся к одному результату без гонки.
- Поток в единой транзакции:
  1. Найти ключ. Если `COMPLETED`, повторить: повторно получить ресурс и вернуть его.
  2. Иначе зарегистрировать ключ (`IN_FLIGHT`). Если регистрация не удалась (уже есть),
     бросить конфликт 422.
  3. Создать отправление, записать строку outbox и пометить ключ `COMPLETED` с
     итоговым `resource_id`.
- Ключи имеют срок действия (`expires_at`); планируемая джоба чистит истёкшие строки,
  чтобы таблица оставалась ограниченной.
- Ключ в состоянии `IN_FLIGHT`, возвращённый клиенту, означает, что запрос
  обрабатывается — клиенту следует повторить с backoff.

## Альтернативы
- **In-memory/Redis-карта дедупликации**: отклонена — теряется при перезапуске, не
  разделяется между инстансами, нет долговременной гарантии.
- **Uuid в payload как естественный ключ**: работает, но стандартный подход с
  заголовком более интероперабелен и явен.
- **Идемпотентность только по id-колонке**: не дедуплицирует два разных запроса,
  которые *означают* одно и то же логическое создание.

## Последствия
- Безопасные ретраи и корректная конкурентность для создания.
- Дополнительная таблица и чуть больший write-set создания (один insert + один update).
- Клиенты обязаны передавать стабильный уникальный ключ на каждый логический запрос
  (задокументировано).
