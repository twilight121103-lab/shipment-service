# ADR-001: Архитектура системы

## Статус
Принято

## Контекст
Сервис отправлений должен быть production-ready, тестируемым изолированно и
независимо развиваться. Рассматривались два широких варианта: слоистая архитектура
(3-tier) и гексагональная/чистая архитектура. Строго слоистая проще в описании, но
приводит к прямой зависимости сервисных классов от Spring/JPA/RabbitMQ, что
усложняет юнит-тестирование бизнес-правил и затрудняет переиспользование домена.

## Решение
Принять pragmatism-подход к чистой/гексагональной архитектуре с разделением на
четыре уровня:

```
com.example.logistics
├── domain         # агрегат, value objects, конечный автомат, порты (интерфейсы)
├── application    # use-case сервисы, команды, query-объекты, события
├── infrastructure # адаптеры JPA, адаптеры RabbitMQ, конфигурация Keycloak/OAuth2, веб-фильтры
└── interfaces     # REST-контроллеры, DTO, глобальная обработка исключений
```

- Пакет **domain** зависит только от JDK. В нём находятся агрегат `Shipment`, его
  value objects, конечный автомат статусов и интерфейсы out-портов
  (`ShipmentRepository`, `OutboxRepository`, `IdempotencyStore`, `MessagePublisher`,
  `TrackingNumberGenerator`).
- Пакет **application** реализует use cases и владеет границами транзакций. Он
  зависит от портов домена, но никогда — от деталей инфраструктуры.
- Пакет **infrastructure** предоставляет адаптеры (JPA-репозитории, RabbitMQ
  publisher/consumer, OAuth2 resource server) и конфигурацию Spring.
- Пакет **interfaces** маппит HTTP в application-команды/запросы и формирует ошибки
  формата RFC 7807 problem+json.

Используются только 5 портов. Это позволяет избежать «пустых интерфейсов» и
переусложнения, оставляя бизнес-логику независимой от фреймворков.

## Альтернативы
- **Слоистая архитектура (3-tier)**: отклонена, так как связывает бизнес-правила с
  фреймворками, затрудняя юнит-тесты и переиспользование.
- **Полный DDD с шинами команд/запросов (в стиле Axon)**: отклонена как излишняя
  сложность для текущего размера; сервисный слой с портами даёт ключевые выгоды без
  лишней церемонии.

## Последствия
- Бизнес-правила легко покрываются юнит-тестами без Spring-контекста.
- Замена PostgreSQL другим хранилищем (или RabbitMQ на Kafka) требует только нового
  адаптера и не затрагивает домен.
- Немного больше шаблонного кода (маппер между доменом и JPA-сущностью), чем у
  простого `@Entity`-агрегата, что принято в обмен на развязку.
- Архитектура остаётся компактной: без избыточного числа слоёв абстракции.
